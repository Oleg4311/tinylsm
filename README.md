# tinylsm

Встраиваемое хранилище «ключ-значение» на основе LSM-дерева, написанное на Rust **без единой зависимости** (proptest нужен только тестам). Журнал упреждающей записи, SSTable с контрольными суммами и фильтрами Блума, уровневое уплотнение, снимки, атомарные пакеты и восстановление после сбоев.

Главная идея проекта не в скорости, а в том, что **надёжность проверяется, а не обещается**: файловая система спрятана за интерфейсом, и тесты «убивают процесс» на каждой возможной точке записи на диск, затем имитируют потерю питания и проверяют, что база открывается и не потеряла подтверждённое.

```
cargo run --release --bin tinylsm -- ./mydb put привет мир
cargo run --release --bin tinylsm -- ./mydb get привет
```

## Использование как библиотеки

```rust
use tinylsm::{Db, Options, WriteBatch};

let db = Db::open("./mydb", Options::default())?;
db.put("user:1", "Ада")?;

// пакет применяется атомарно: после сбоя виден целиком или не виден совсем
let mut batch = WriteBatch::new();
batch.put("user:2", "Линус").delete("user:1");
db.write(&batch)?;

// снимок: чтения не видят более поздних записей, даже после сброса и уплотнения
let snap = db.snapshot();
db.put("user:2", "изменено")?;
assert_eq!(db.get_at(&snap, b"user:2")?.unwrap(), b"Линус");

// просмотр диапазона [от, до) по возрастанию ключа
for item in db.scan(Some(b"user:"), Some(b"user;"))? {
    let (key, value) = item?;
}
```

Подключение из git: `tinylsm = { git = "https://github.com/Oleg4311/tinylsm", tag = "v0.1.0" }`. В crates.io пакет пока не публикуется.

### Командная строка

| Команда | Что делает |
|---|---|
| `put <ключ> <значение>` / `get <ключ>` / `del <ключ>` | базовые операции (`get` возвращает код 1, если ключа нет) |
| `scan [от [до]]` | пары из диапазона `[от, до)` |
| `fill <N>` | записать N тестовых пар |
| `stats` | файлы и размеры по уровням |
| `compact` | сбросить память на диск и слить уровни |
| `verify` | прочитать всё и проверить все контрольные суммы |

Готовые бинарники (Linux, Windows, macOS) лежат в [релизах](https://github.com/Oleg4311/tinylsm/releases). Проверка: `sha256sum -c SHA256SUMS` и `gh attestation verify <файл> --repo Oleg4311/tinylsm`.

На обычном ноутбуке `fill 300000` (пакетами по 1000 с fsync) занимает меньше секунды, `verify` по ~10 МБ — около 0,2 с. Это не бенчмарк, а ориентир порядка величины.

## Как устроено

```
запись ──► WAL (fsync) ──► memtable ──(сброс)──► L0 ──(уплотнение)──► L1 ──► … ──► L6
                                                   файлы SSTable: блоки с CRC, индекс, фильтр Блума, подвал
```

* **WAL.** Запись журнала: `crc32 | длина | данные`, CRC покрывает и длину. Один пакет — одна запись, поэтому атомарность даёт сам журнал. При восстановлении оборванная или испорченная **последняя** запись считается недописанным хвостом и отбрасывается; испорченная запись, за которой есть ещё данные, — это ошибка `Corruption`: молча пропустить середину журнала значило бы потерять подтверждённые записи.
* **Версии.** Каждая операция получает номер. Записи упорядочены по (ключ ↑, номер ↓), поэтому для ключа первой идёт самая новая версия. Снимок — это просто номер: чтение берёт самую новую версию не новее него.
* **SSTable.** Блоки данных по ~4 КиБ, у каждого CRC-32; индекс, фильтр Блума (10 бит на ключ, ≈1% ложных срабатываний) и подвал с магическим числом и собственной суммой. Порча любого байта обнаруживается при чтении: об этом тест, который по очереди портит байты файла.
* **Манифест.** Журнал изменений набора файлов (в том же формате записей, что и WAL) плюс файл `CURRENT`, переключаемый через `rename`. При каждом открытии пишется новый компактный манифест.
* **Уплотнение по уровням.** L0 сливается в L1 при ≥ 4 файлов; уровень *n* ≥ 1 вмещает в 10 раз больше предыдущего, лишний файл сливается с пересекающимися файлами следующего уровня. Старые версии ключа сохраняются, пока их видит хотя бы один живой снимок. Надгробие (удаление) убирается, только если глубже нет файлов, которые могут содержать более старые версии ключа.
* **Удаление устаревших файлов.** Файл стирается, когда исчезает последний читатель его таблицы (итераторы и снимки удерживают версию), а не в момент уплотнения.
* **Блокировка.** Файл `LOCK` не даёт открыть базу второму процессу (`Error::Locked`).
* **Отказ после ошибки записи.** Если запись в журнал или манифест не удалась, база переходит в аварийное состояние и отвечает ошибками, пока её не откроют заново (после неудачного fsync нельзя считать, что на диске).

## Как проверяется надёжность

Все обращения к диску идут через трейт `Env`. Есть настоящая реализация и `MemEnv` — файловая система в памяти, моделирующая потерю питания:

* мутирующие операции (создание, дозапись, fsync, переименование, удаление, fsync каталога) — «точки отказа»: на выбранной точке «процесс» умирает;
* затем `power_loss`: несинхронизированные хвосты файлов обрезаются (иногда последний кусок оказывается испорченным), а изменения имён после последнего fsync каталога сохраняются лишь частично (случайным префиксом журнала операций).

Тесты (всего 44):

| Набор | Что проверяет |
|---|---|
| `tests/crash.rs` | для трёх сценариев **смерть на каждой точке записи** (сотни точек на сценарий) + потеря питания → база открывается; всё подтверждённое (`sync`) на месте; итоговое состояние равно результату некоторого **префикса** операций (пакеты целиком); база после восстановления работает. Отдельно: смерть **во время восстановления** на каждой его точке; несинхронизированные записи сохраняются только префиксом |
| `tests/model.rs` | случайные последовательности операций (запись, пакеты, удаления, чтения, диапазоны, сброс, уплотнение, переоткрытие, снимки) сравниваются с `BTreeMap`; параметры минимальные, чтобы уровни переполнялись постоянно; 4000 операций доходят до глубоких уровней |
| `tests/kill9.rs` | настоящий `kill -9` / `TerminateProcess` рабочего процесса на реальной файловой системе в случайный момент, 6 раундов подряд; блокировка от второго процесса |
| `tests/api.rs` | CLI, порча байта в SSTable (ошибка, а не неверные данные), оборванный и испорченный журнал, граничные аргументы, снимки через сброс и уплотнение |
| модульные | CRC-32 по эталонным векторам, фильтр Блума, разбор мусорных данных без паник, порча любого байта SSTable, обрезка файлов |

**Мутационная проверка.** Я вручную ломал код и убеждался, что тесты это замечают: убрать fsync манифеста, SST, `CURRENT.tmp`, каталога после создания файлов, игнорировать `sync` в WAL, не проигрывать последний журнал, не учитывать снимки при уплотнении, всегда выбрасывать надгробия, искать в L0 от старых файлов к новым, не склеивать пересекающиеся файлы, не учитывать номер при поиске блока, игнорировать номер снимка в просмотре — все пойманы.

**Что нашли сами тесты** (ещё до первого выпуска):

* при уплотнении надгробие выбрасывалось, если глубже нет файлов, пересекающих *входные* файлы, но диапазон слияния шире — туда входят целые файлы следующего уровня; удалённые ключи «воскресали» после `compact` (поймал модельный тест, остался как регрессия в `tests/model.proptest-regressions`);
* `ManifestState::apply` менял состояние до обнаружения ошибки в правке — после отказа состояние было наполовину применено.

## Честные ограничения

* **Один процесс, один мьютекс.** Сброс и уплотнение выполняются синхронно внутри записи, пока они идут, чтения и записи ждут. Фоновых потоков нет — это упрощает проверку корректности, но не годится для больших нагрузок.
* **Нет сжатия, префиксного сжатия ключей, кэша блоков в виде LRU** (кэш — простой, сбрасывается целиком), нет транзакций сверх атомарного пакета, нет слияния значений, TTL и семейств колонок.
* **Просмотр диапазона** копирует нужную часть memtable при создании и выбирает минимум линейным проходом по всем файлам (O(число файлов) на шаг).
* Значение и ключ целиком в памяти: ограничения 16 МиБ и 64 КиБ. Пустой ключ запрещён.
* **Потеря питания моделируется, а не проверяется на железе.** Симулятор считает, что порядок операций с именами сохраняется (теряется только префикс), и портит только последний записанный кусок файла; переупорядочивание страниц и враньё накопителя про fsync не моделируются. Реальный `kill -9` проверен, настоящее отключение питания — нет.
* На не-Unix платформах fsync каталога — пустая операция (в стандартной библиотеке нет переносимого способа); на Windows сохранность переименований опирается на журналирование метаданных NTFS.
* Формат файлов пока не версионируется и может измениться до 1.0.

## English

**tinylsm** is a dependency-free embedded LSM-tree key-value store in Rust: write-ahead log, SSTables with per-block CRC-32 and Bloom filters, leveled compaction, snapshots, atomic write batches, range scans and crash recovery. The point of the project is *verified* durability: all disk access goes through an `Env` trait, and an in-memory `MemEnv` kills the "process" at **every** possible write point, then simulates power loss (unsynced tails truncated or garbled, unsynced directory changes kept only as a random prefix). After each of hundreds of such crashes the database must open, keep everything acknowledged with fsync, and show a state equal to some *prefix* of the write sequence (batches all-or-nothing). Also tested: a model test against `BTreeMap` with random operations, flushes, compactions, reopens and snapshots (proptest); real `kill -9` of a writer process on the real filesystem; byte-flip corruption detection in SSTables; hand-made mutations of the code that the tests had to catch. The tests themselves found a tombstone-resurrection bug in compaction before the first release.

Limitations, honestly: single process, one global lock, synchronous flush and compaction (reads and writes wait), no compression, simple scan, power loss is simulated (page reordering and lying disks are not modelled; real `kill -9` is tested, real power cuts are not), directory fsync is a no-op off Unix, on-disk format is not yet versioned.

Install from git: `tinylsm = { git = "https://github.com/Oleg4311/tinylsm", tag = "v0.1.0" }`; CLI binaries with SHA-256 sums and build attestations are attached to each release.
